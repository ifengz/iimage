# Lessons

## 2026-03-20

- 当用户明确给出新的 UI 目录或设计源时，立即停止沿用旧稿，先读取新目录下的设计稿和代码稿，再继续实现。
- 在开始实现前，如果同目录里同时存在多个 UI 参考源，必须先确认当前唯一基线文件，避免按过期稿开工。
- 用户指出布局在宽屏下失衡时，优先检查是否用了固定像素侧栏和缺少主区 padding，而不是只缩中间卡片。
- 只要页面里有“应用”动作，就必须给出可见反馈；这类工具里最直接的反馈就是把实际发送给模型的 prompt 展示出来。
- 入口文件这类会直接导致白屏的核心文件，不能先删再慢慢重写；必须在同一个补丁里完成替换，确保任意时刻都还能编译。
- 用户用草图重新描述布局时，必须按“上中下”和“左中右”逐句翻译成页面骨架，不能把“上下结构”误做成“右侧上下堆叠”。
- 用户如果继续说“卡片还是太大”，优先先统一首屏主卡的总高度，再把超出的内容改成卡片内部滚动，不能只零碎缩字号和 padding。

## 2026-03-21

- 看到页面里写死的展示尺寸时，不能直接推断成“实际发送给模型的原图尺寸被改掉了”；必须先核对真实上传链路和发送数据，再判断是不是 bug。
- 用户说“删掉某类内容”时，不能自己扩成“全部删光”；如果列表里可能有保留项，必须先核对具体删哪几个、留哪几个，再改测试和代码。
- B 区自动生成出来的 prompt 和 C 区手动改过的 prompt，不能共用同一套“必须先保存”规则；只有 C 区被手改过，才应该要求用户点保存。
- 只要用户明确说“生成结果不该是两张拼一起”，就不能只盯着预览组件；要先检查发给模型的 prompt 有没有明确禁止对比图、拼图、左右分屏。
- 用户说“颜色还是没变”时，不能只看静态组件测试过没过；必须核对真实运行态里的驱动数据有没有真的变化，避免测到假通过。
- 用户指出“底部状态栏应该居中”时，不能只把内容留在唯一一行里就算完成；必须检查整条状态信息在容器里的对齐方式，避免默认挤到左边。
- 用户说“会呼吸但没变色”时，不能把“阶段切换时换过一次颜色”当成完成；必须确认动画过程本身也带颜色变化。
- 用户指出悬浮按钮位置错了时，不能只看按钮能不能点；必须检查这个按钮有没有错误地进入布局流，顺手把旁边的内容挤偏。
- 用户说“点完第一条后，后面的 2、3、4、5 没有继续往下填”时，不能只验证第一格能写进去；必须检查回填后的接收目标有没有自动推进到下一个输入框。
- 用户说“这层东西挡住原图、要改成可选择”时，不能只修透明度；必须连同触发时机一起改成“手动执行 + 显示开关”。
- 用户说“点完 OCR 还在第一个框里打转”时，不能只检查点击事件有没有触发；必须顺着接收目标状态看完整条链路，确认每次写入后有没有把目标框顺延到下一个 `before` 输入框。
- 用户说“A 区预览错了、要适应卡片大小”时，不能只拿大图看一眼就下结论；必须同时拿大图和小图复现，确认是不是只写了“缩小大图”却没处理“放大小图”。
- 用户说“按钮样式还是不一样”时，不能只看按钮颜色和文案；必须把位置、提示归属、高度、字号和悬浮动效一起对齐到同一套按钮系统。
- 用户说“直接去看 B/C 区按钮代码”时，不能只复制按钮本体；必须连同外层按钮栏和父容器 padding 一起核对，否则视觉上还是不会在一条线上。
- 用户拿红框继续说“还没对齐”时，不能拿先前单测通过当完成；必须回到真实浏览器页面看三块底部栏的运行态截图，再决定是按钮本体问题还是外层容器问题。
- 当 app 编译配置里出现 `vitest/globals` 这种测试专用类型时，不能当成小事；必须把测试类型挪到单独的测试配置里，避免正式边界继续变脏。
- 当 `tsc -b` 会顺手产出 `vite.config.js` 这类生成产物时，不能把它们和源码一起当成“正常文件”；必须收口成单一真相，不然后面很容易改串。
- 当缩略图里有“前/后”这种视图切换时，不能只做成鼠标可点的 `div`；必须让它变成真正的按钮，键盘用户才不会被挡在门外。
- 当 README 里的包名和 `package.json` 对不上时，不能当成文字问题看；它会直接把新接手的人带去装错依赖。
